# Changelog

Every branch adds its own entry here, under a `## YYYY-MM-DD` heading dated between the day it
started and the day it lands (UTC). Entries describe the change; they never cite
facts that only exist after the owner merges. `npm run changelog:guard` enforces this.

From 2026-10-17 each branch records its change in its own fragment under `changelog/` instead ([ADR-0027](wiki/decisions/ADR-0027%20Changelog%20entries%20are%20per-branch%20fragment%20files.md)); the entries below are the history before that switch.

## 2026-10-17

- Each branch now records its change in its own new fragment, `changelog/<YYYY-MM-DD>-<slug>.md`, instead of an entry in the shared changelog file, so two open pull requests no longer conflict there (ADR-0027, which supersedes ADR-0007 and restates its rule that entries cite no post-merge facts). `npm run changelog:guard` requires at least one valid new fragment for a branch that changes a non-exempt file: named with a real date between the day the branch started and today (UTC) and a lower-case kebab-case slug, holding a `- ` entry outside code fences. It refuses an invalid fragment even beside a valid one, a change to or deletion of a fragment already on main, and any change to `CHANGELOG.md` once main holds a fragment, and tells a branch that still writes there to move its entry. This pull request is the one transition: it adds a line here and its own fragment. `governance:check` now refuses live text that still asks for the old entry and excludes fragments as history, and the rules, `CLAUDE.md`, `README.md`, runbooks, Sandcastle prompts and memory guard are repointed. The unused `addedLineNumbers` helper is retired.

- The Sandcastle AFK wrapper now treats a changelog fragment, `changelog/<YYYY-MM-DD>-<slug>.md` (ADR-0027), as documentation it may land unattended, so a documentation-only branch that records itself with a fragment is not refused as code. `scripts/lib/paths.ts` names the folder and the fragment pattern once; any other file under `changelog/` is still refused. No guard requires fragments yet, and `CHANGELOG.md` stays the required record. The `governance:check` exclusion for fragments moves to the slice that adds the first one, because the check refuses an exclusion that matches no file.

- The per-branch changelog fragments plan is now approved, and its two slices are build tickets: first recognising `changelog/` fragments as documentation in the AFK landing rule and `governance:check`, then switching `changelog:guard` to require a fragment per branch.

- `npm run audit` now audits this fork only and checks more than the commit a pull request landed as. Its config named the upstream repository while origin is the fork, so every fork pull request came back unverified and the audit failed on a clean history (audit finding A07). It now names `Zimfra/software_testing` and starts after `f9c1b9d`, the inherited commit just before the fork's first pull request merge, as the owner decided on 2026-10-16; a boundary that is not on main's first-parent history is an error. Each later commit passes only if its pull request targeted `main` (audit finding A08: a merged PR into another branch with a matching commit used to pass) and was merged by a code owner named in `.github/CODEOWNERS` on main just before that commit landed, so an owner change later on does not fail earlier landings. A `gh` answer missing a field is now an error instead of a failed verdict. The CODEOWNERS parser moved to `scripts/git/code-owners.ts`, which `npm run pr` also uses.

- `npm run pr` and `npm run audit` now fetch origin's main into `refs/remotes/origin/main` explicitly and compare the commit that fetch captured. Before, they ran `git fetch origin main` and read the tracking ref, which a narrowed `remote.origin.fetch` leaves stale while the fetch succeeds, so the audit could miss a direct push and `npm run pr` could pass a branch that is behind main (audit finding A09). A failed fetch, a missing main or a non-commit stays an error, no other remote ref is rewritten, and the Sandcastle AFK wrapper, which already fetched this way, now shares the same refspec.

- A proposed plan and ADR-0027 replace the shared changelog edit with one dated fragment file per branch under `changelog/`, after two open pull requests conflicted on the same `CHANGELOG.md` section. The plan has two build slices: first teaching the AFK wrapper and the governance check that fragments are documentation, then switching the guard with a one-time transition for the pull request that makes the switch, and retiring every rule, prompt, runbook and config reference that names `CHANGELOG.md`.

- The pre-push state check now notices content changes that `git status` hides. Its working-tree snapshot covered only the status listing, so rewriting an already-modified or untracked file, flipping its executable bit or retargeting an untracked symlink went unseen (audit finding A06). It now also hashes, for each listed path, the file's bytes and executable bit or a symlink's target text, without following links; a path under a directory that resolves outside the work tree is recorded and never read, and an unreadable file stops the push instead of passing. Files are hashed in chunks, so size is not capped by one read, and a listed name that is not valid UTF-8 stops the push rather than passing unchecked. Ignored files and the contents of a directory listed as one entry (a nested repository or submodule) stay outside the snapshot, and it still holds only hashes. The refusal message now also names an editor or other program changing a file during the check.

- The audit remediation records close S02 after its merge and point the project at S04. From S04 on, each ticket's own pull request marks it done, so no separate closeout pull request follows.

- `spawnRunner` in `scripts/git/pr-ready.ts`, which starts git, node, npm and gh for `npm run pr` and the Sandcastle AFK wrapper, now follows the explicit-checkout rule in `scripts/lib/git.ts`. With an explicit `cwd` it drops every `GIT_` variable, so an inherited `GIT_DIR`, `GIT_WORK_TREE` or `GIT_INDEX_FILE` can no longer send git, or git launched through node or npm, to another repository (audit finding A03). Without a `cwd` it still keeps the hook's repository and drops only injected configuration and history, so `npm run pr` and the AFK wrapper, which pass none, behave as before. Tests drive the real runner against a decoy repository and check that its HEAD, refs, configuration, index and files are unchanged, and that without a `cwd` git keeps the hook's index while an injected graft file, replace-ref base or `GIT_NO_REPLACE_OBJECTS` changes nothing it reads. An explicit `cwd` also drops `GIT_ASKPASS` and `GIT_SSH_COMMAND`, which no current caller needs.

- The pre-push state check (`scripts/git/git-state.ts`) no longer compares `branch.<name>.vscode-merge-base`, a key the VS Code Git extension writes when it first sees a branch and git never reads. VS Code often wrote it while the check ran, so the first push of every new branch was refused as if a test had changed git state. Every other local and per-worktree key is still compared, and tests pin that look-alike keys (`branch.<name>.merge`, a longer VS Code key, the same variable in another section) are still refused.

- The audit remediation records now close S01 after its merge, record the owner's execution defaults for the remaining job specs (containment proof from CI runners only, offline controls only, one ticket at a time, the machine account as local commit author) and close the inactive-GitHub-profile issue as resolved in the checkout now used. A new issue records that VS Code writes a `vscode-merge-base` key into local git config during the pre-push check, which makes the first push of a new branch fail.

- The compliance harness tests no longer hand a child process the caller's environment. The scenario-setup test passed `setup_sandbox` a runner that inherited `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` and injected configuration, so under a hook its `git init` and shell setup commands could act on another repository (audit finding A02). Every Python test spawn now passes `run_comply.isolated_env`, and a new `evals/compliance/test_fixture_env.py`, the Python twin of `scripts/toolchain/fixture-env.test.ts`, refuses a spawn in `evals/compliance/test_*.py` without it in the common forms: direct, renamed and annotated aliases, a spawner function passed as a value or stored, and an env written into or emptied after it was built. It reads the syntax tree, and its docstring lists the forms it does not follow. Its decoy-repository controls show that the old runner rewrites a decoy named by inherited routing and receives injected configuration, and that the isolated runner initialises the fixture and leaves the decoy's HEAD, refs, configuration, index and files unchanged.

It fetches `origin/main` once before the loop and once after it, so a stale tracking ref cannot cause a spurious refusal, an unreachable origin is reported with the other refusals, a fetch that throws or leaves no `origin/main` counts as failed, a fetch that fails after the loop says the loop already ran and nothing was pushed, a git hook the loop wrote or changed (compared by content before and after, including from a linked worktree, and compared before any git command that could run it) exits 2, a hooks directory that cannot be read is refused before the loop, and only `git merge-base` exit 1 is read as "no history in common"; reports the code refusal together with the other refusals, names a branch with no history in common with `origin/main`, compares the local git config key by key (a multi-line value cannot hide a change), and exits 2 instead of 1 when a code refusal coincides with stranded or deleted work or when a notice comment could not be posted.
