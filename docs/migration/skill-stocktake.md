# Zimi skill stocktake

This is ECC `skill-stocktake` (full mode) run on 2026-10-09 against the 34 Zimi skills staged at
`docs/migration/zimi-skills/` (Zimi `main` @ `9fb36b2`). `wiki-memory` was migrated and reviewed in Phase 3 and was not
re-evaluated, which leaves 33 skills.

**How it was run**
- Phase 1 built the inventory with Python, because the stocktake's `scan.sh` needs `jq`, which is not installed. Usage
  counts are unavailable: none of these skills has run in this repository.
- Phase 2 used two general-purpose subagents with the stocktake checklist. They compared each skill against ECC's
  skills and rules and against the decisions already made for this migration.

## Owner decisions (2026-10-09)

These answers are quoted from the owner. Baseline revisions in `.claude/skills/import-baseline.json` cite this section
as their approval record.

**What follows from the decisions**
- **TDD.** Zimi's `tdd` content is dropped entirely, and ECC's `.claude/rules/ecc/common/testing.md` governs. This
  replaces the stocktake's "merge into a testing rule" verdict.
- **Nesting depth.** It stays at 4, ECC's limit, which `eslint.config.ts` enforces. Zimi's coding-standards said 3.
- **Em dashes.** No skill in `.claude/skills/` may contain an em dash. `skills:lint` enforces this.

## Rules to distill (Phase 7)

Lasting rules that the subagents flagged in each skill, including skills that are retired or merged. Phase 7
`rules-distill` turns them into `.claude/rules/zeem/*.md` files, or marks each one as already covered by ECC. `tdd`'s
items are dropped by the owner's decision.

### architecture-principles
- Add an abstraction or interface only after two real consumers need it; one consumer is a guess about the second.
- No feature flags or backwards-compat shims for code that can simply be changed; inspect actual consumers first.
- Definition of done: code, dependency declarations (manifest + lockfile in the same commit), documentation beside the behavior, and the work record all land in the same PR; work that cannot carry all four is too big and must be split.
- Discovered work gets a work-record entry, not an inline fix, unless it blocks the current task (then fix it and say so in the commit).
- Every open work item names a concrete blocker; a decision is a work item.
- A completed item cites the PR or merge commit that completed it, never an implementer's summary alone.

### automate-me
- Codify an owner preference only after it recurs in 2+ independent sessions and is not contradicted elsewhere; a one-off statement is noise.

### branch-review
- A builder session never certifies its own work; review runs in a different session or agent than the one that wrote the change.
- Review against pinned SHAs, never branch names.
- Reviews report findings; they never approve or merge a PR - only the owner merges.

### coding-standards
- Validate at real boundaries (user input, external APIs, network, file content); do not add defensive checks against internal code or stdlib/framework guarantees.
- Comments default to none; write one only for a non-obvious why (hidden constraint, bug workaround, invariant).
- Test effort is proportional: pure logic gets a unit test; no test harness disproportionate to a tiny glue script.
- Prefer stdlib/no dependency for small scripts; any added dependency carries a one-line justification in the commit that adds it.
- Match each language's own naming convention (camelCase TS/JS, snake_case Python, kebab-case file names and CLI flags).

### design-actions
- Any action that spends money, applies infrastructure, deletes branches/worktrees/cloud resources, or sends data outside the local workspace needs explicit owner authorization checked before the side effect; a CLI flag cannot grant it.
- Repo CLI verbs validate all inputs and refuse before any side effect, reporting every refusal reason, with exit codes per scripts/lib/cli.ts (0 ok, 1 refused, 2 error).

### diagnose-bug
- Do not fix a defect you have not reproduced; the repro command becomes the failing regression test.
- A prevention names a check that exists and fails on the original defect, or states 'none: <reason>'; 'be more careful' is not prevention.

### diagram-wiki
- A diagram must not show a proposed, failed or unobserved path as a working edge; every arrow traces to a cited source.

### documentation-standards
- Docs that a newcomer lands on define each term on first use and state the reason behind a convention, preferring a real worked example (PR number, actual failure) over a hypothetical.
- README is orientation only (what, layout, quick start, links); depth lives in docs/ or the wiki.
- A doc about version-sensitive facts (tooling, hardware, external services) states its capture date and how to re-verify it.
- Document only the provider/tool actually verified working; an alternative discussed during design is never written up as the live integration.
- Standards docs drafted by an agent without owner input start with a '> **Status:** draft' line, removed only after the owner confirms.

### domain-modeling
- Record an ADR only when the decision is hard to reverse, surprising without context, and the result of a real trade-off.

### eval-driven-development
- An eval or verifier is trusted only after it is shown to fail on a deliberately broken control; an agent's own success message is evidence to inspect, not verification.
- Structural checks (lint, schema) do not prove agent behavior; report structural, selection and outcome results separately and name unrun cases.

### fullstack-engineer
- Read the nearest existing module that does something similar in full before writing, and match its conventions.
- State the plan in 3-6 lines (what changes, which files, what could break); if it needs more, the task is too big - say so instead of building.
- Find importers/callers (rg) before editing, not after.
- Challenge a brief that duplicates an existing capability or crosses an ownership boundary before the first edit.
- Wiki changes are committed separately from code on the same branch with a `docs(wiki):` subject.
- The builder never merges, closes its own work item, or writes its own verdict; the owner merges the PR.

### grill-plan
- Never resolve an owner decision by inferring what the owner would say; mark it awaiting input and reuse answers already given.
- Do not ask the owner a question a command or file read can settle; run it instead.

### learn-from-failure
- A prevention is a check that runs in an existing test/CI command and is proven to fail on the original defect before passing with the fix; a check with no runner prevents nothing.
- Never repoint a prevention at a nearby file to make a record look complete; write 'none: <reason>' instead.
- Drive-by fixes are limited to mechanical issues in lines this change touched; anything else is reported as an observation, not fixed.

### maintain-verification-skill
- When documentation and behavior disagree, decide doc drift vs product regression; never edit docs to paper over a regression.

### manage-branch
- Agents never push to or merge into main; all work lands via a GitHub PR the owner merges.
- Keep a published branch current by merging main into it; never rebase or force-push published history.
- Stage files explicitly; never `git add -A` from a dirty tree.
- Never discard, absorb or clean up another session's uncommitted work or worktree; delete only branches confirmed merged.

### plan-tickets
- Build tickets are created only from a plan the owner approved by merging its PR; an agent-written status label never establishes approval.

### principle-laziness-protocol
- Prefer deletion over addition when refactoring; make the smallest diff that solves the problem.
- When a task asks you to thread a new signal through types, schemas, or pipelines, stop and look for a more direct path.
- Put a repeated decision behind one source of truth instead of repeating it.

### principle-minimize-reader-load
- Collapse wrappers with one caller, adapters with one implementation, and pass-through layers that repeat the same methods.
- Shrink state scope: returns over mutation, locals over fields, fields over module state, module state over globals; derive instead of sync.
- A new reader should answer 'where does X come from?' and 'what can change X?' in under 30 seconds.

### principle-redesign-from-first-principles
- Integrate a new requirement as if it had been there from the start, and update every reference (types, docs, examples, rationale); design the whole, deliver it incrementally.

### publish-to-site
- Content that leaves the repository (public page, gist, external post) needs owner authorization for that destination, and a redaction pass on the final rendered output: secrets, third-party identities, hostnames, LAN addresses, absolute paths containing a username, unsettled decisions, and quoted private messages.

### research-trends
- Every external claim recorded in the wiki cites a primary source with the date it was read; a search snippet or roundup article is a lead, not a source.

### resolve-conflicts
- Never rebase or force-push published history; bring main in with a merge.
- Stage files by name, never `git add -A`.
- Regenerate a generated file from its source; never hand-merge it.

### standards-reinforcement
- A cleanup or refactor change adds no new behavior; a change that would alter behavior stops and is raised as separate work.
- Before fixing an apparently unenforced standard, plant the violation and confirm the check really misses it.
- Agents report a branch as ready for human review; never as approved.

### verify-work
- A verifier judges the artifact and its own runs, never the implementer's account; a number it did not reproduce is unverified.
- A verifier never edits, commits, or approves what it judges, and discloses self-review.

### wayfinder
- An agent never answers a decision that belongs to the owner, and never turns an open question into an assumption.

### write-plan
- A plan records only settled decisions; an open decision stops the plan instead of being written into it.
- A branch never approves its own plan; approval is the owner merging the PR.

### write-skill
- A new skill, rule, or script retires what it replaces in the same PR and repoints every live reference; historical records stay as written.
- Never prescribe a check that nothing runs; an unexecuted prevention reports false green.
- Agents may draft skills; only the owner approves by merging the PR.
